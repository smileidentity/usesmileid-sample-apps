# Shipping the iOS sample to the App Store

**Status:** READY FOR THE ACCOUNT ACTIONS. Every item but the camera panel is landed and walked (§7.1); what is left needs an App Store Connect account, and `docs/app-store-manual-steps.md` is that list. This is the plan `ios-port-hardening.md` "Where to pick up" item 8 says does
not exist yet, and it closes that half of the item — the device lane is the other half and has its own
doc. Scope: the App Store Connect listing for `com.usesmileid.sample.ios`, the archive that backs it,
the store-art pipeline, and a TestFlight lane with an App Store lane behind it. Not the app's
behaviour: the port is functionally complete through #81 and this plan adds no screens.

Android shipped first and `play-release-android.md` §8 lists what travels. Everything there that is
not Play-specific is inherited here rather than re-decided, and where iOS diverges the divergence is
argued from this tree rather than from the platform in general.

**Settled up front, so the work does not open by re-asking.** Carried from the Android rulings unless
noted:

- The **bundle id is `com.usesmileid.sample.ios`**, already declared in `ios/App/project.yml` and
  asserted by the shell's own spec test. It is permanent from the first upload.
- The **store name takes the spec name**, "UseSmileID Sample", as Play's title did.
- **Phone-only** — §6.2 is the code that decides it, and it is the same code shape Android's §6.2 read.
- The **app icon has landed** (#81) from `svgs/ios.svg`, gated by `scripts/generate_app_icon.py --check`
  in `ios/verify.sh`. §4 says why nothing here touches it.
- **No fastlane.** Bare `xcodebuild archive` plus `exportArchive` with a committed export-options
  plist. Adding a dependency to this repo needs an owner's go-ahead and this does not need one.
- The **product paragraphs are shared with Play** — `play-release-android.md` §8 fixed that, and §5
  here records only what the App Store's own fields force to differ.

## 1. What is blocking, read out of the build files

Seven items. One is irreversible, three stop an upload at App Store Connect rather than at build
time, and one is a default nobody chose.

1. **There is no distribution signing path at all.** `ios/App/project.yml` declares
   `CODE_SIGN_IDENTITY: "-"` (ad hoc) for the simulator and `Apple Development` for a device. Nothing
   in the tree archives for distribution, and **no team is committed** — `DEVELOPMENT_TEAM` is passed
   on the `xcodebuild` line, which is deliberate and must stay that way (the comment in `project.yml`
   says why: committing one makes every other developer inherit it). §3 says exactly what to add.
2. **Signing identity and bundle id are permanent from the first upload.** This is the item that
   cannot be corrected afterwards, and it is the reason the first upload is an owner action rather
   than a CI trigger. Unlike Android there is no key to reuse: App Store distribution certificates
   are account-scoped, and the App Store signing identity belongs to Apple, not to this repository.
3. **`ITSAppUsesNonExemptEncryption` is absent from the Info.plist.** `ios/App/Info.plist` is
   generated by XcodeGen from `project.yml`'s `info.properties` and is gitignored (`.gitignore:22`),
   so the key belongs in `project.yml`. Without it every single TestFlight build stops and waits for
   a human to answer the export-compliance question in App Store Connect before testers can install
   it — a lane that is green and still delivers nothing.
4. **There is no `PrivacyInfo.xcprivacy`.** The app reads `UserDefaults` in two places —
   `UseSmileIDSampleLaunchArguments.swift:56` (the argument domain) and `UseSmileIDSampleStore.swift:195`
   (the six settings switches) — which is a required-reason API. Missing declarations come back as an
   ITMS-91053 email after the upload has already been accepted, so it fails late and silently. §6.3
   covers what the dependency graph does and does not declare for itself, which is the half that has
   to be checked rather than assumed.
5. **`CURRENT_PROJECT_VERSION` is `1` and `MARKETING_VERSION` is `1.0`**, both hard-coded in
   `project.yml:settings.base` with no bump mechanism. App Store Connect rejects a build whose number
   it has already seen for that marketing version, so a wasted upload burns one — the same failure
   mode as Play's `versionCode`, with a smaller blast radius because the number resets per version
   train. §3.1 derives it the way Android derives `versionCode`.
6. **`TARGETED_DEVICE_FAMILY` is `"1,2"`** in the generated project — XcodeGen's default, not a
   decision. It is not declared in `project.yml` at all, which is how it went unnoticed. A universal
   app owes iPad screenshots at 2064 × 2752 and gets Apple's iPad review against a layout that has no
   iPad in it. §6.2 is the code that settles it.

7. **Two usage strings are missing, and one of them is an upload rejection.** Found by comparing
   against the v11 sample's `Info.plist` rather than by reading this tree, which is the argument for
   the comparison. `UseSmileID.framework` references `CLLocationManager`, `CMMotionManager` and
   `PHPickerViewController`; `UseSmileIDBridge.framework` references `LAContext`. App Store Connect's
   missing-purpose-string check (ITMS-90683) runs against the binary's references, not its calls, so a
   referenced `CLLocationManager` with no `NSLocationWhenInUseUsageDescription` fails the upload —
   even though the SDK never prompts. All three Smile ID samples (v11 ×2, the v12 SDK's own) ship it;
   this one did not. §6.6 has the ruling on each of the four references.

**Checked and cleared, so it does not linger as a suspicion:** the deployment target is consistent —
`project.yml` declares iOS 17.0 for the app, `SampleUI/Package.swift` sets the same floor, and the
UI-test bundle's 16.4 is the *runner's* floor, which never ships. The icon asset is 1024 × 1024 with
no alpha channel (PNG colour type 2), which is what App Store Connect requires and what
`scripts/generate_app_icon.py` exists to guarantee.

## 2. Capturing the screenshots

Android's §2 is inherited whole: render from committed, deterministic tests rather than by hand;
fixture-only data in every published frame; commit the rendered set and gate it. What changes is the
renderer and the numbers.

### 2.1 swift-snapshot-testing is already the capture engine

`ios/SampleUI/Tests/SampleUIGoldenTests/` runs **swift-snapshot-testing 1.19.4** with 207 committed
baselines, of which `UseSmileIDSampleScreenGoldenTest` alone holds 109 full-screen renders — products
with and without a session, verifications, verification details, settings, the scan screen. The same
three properties that made Roborazzi the right source on Android hold here:

- **It renders on a simulator at a declared size.** `UseSmileIDSampleGoldenTest` pins
  `width = 393` and derives the height by measuring, so the size is a parameter rather than a device.
- **It is already determinism-hardened**, because the goldens render clock times and the harness
  pins the scheme trait pair rather than reading the runner's appearance.
- **It is already staleness-gated** — a changed baseline fails `ios/verify.sh`, and CI runs that
  script rather than repeating its steps.

### 2.2 Why the goldens are not the frames, and a second test is

This is the one place the Android pattern cannot be copied verbatim, and the reason is arithmetic.
The golden harness renders at 393 pt, which at the pinned simulator's 3× scale is **1179 × 2796**.
The `ios-phone` preset is **1320 × 2868** — 440 × 956 pt. Those are different devices, so reusing a
golden as a frame would either letterbox or rescale, and rescaling a text-heavy screen is visible.

So store art gets its own test at the store device's size, its own output directory and its own
staleness input — which is exactly what Android's `StoreArtTest` is, arrived at from a different
direction. The separation also keeps the property Android's §2.3 argued for: **store art can never
quietly repaint a golden**, because the two write to different directories from different tests.

### 2.3 The one frame a snapshot test cannot produce

Same split as Android, same reason: a live camera preview is not a pure function of state. Five
panels render off-device; the capture panel comes from XCUITest on a real device, which is the runner
`AGENTS.md` §Testing already names for iOS.

| Panel | Source | Why |
|---|---|---|
| Products grid | snapshot test | pure state |
| Token session (linked, counting down) | snapshot test | pure state; the harness already pins the clock |
| SDK capture in flight | **XCUITest on a device** | camera preview cannot render off-device |
| Verifications list, filters populated | snapshot test | pure state, fixtures seeded |
| Verification details + result card | snapshot test | pure state |
| Settings composing the journey | snapshot test | pure state |

The capture panel is written and unrendered, exactly as Android left REL-A9. It is not a blocker:
Apple requires **one** screenshot at the 6.9" size, and five are committed.

### 2.4 The status-bar inset, and the prediction it falsified

`play-release-android.md` §8 warns this explicitly: *"A rendered frame is not a screenshot — it needs
a status-bar inset … Android needed 40dp. iOS will need more, and the Dynamic Island is a larger
obstruction than a punch-hole."*

**The first half is right and the second half is wrong**, which is the argument for measuring rather
than reasoning. Measured the way Android measured it — a probe whose every source row is identifiable
by colour, composed through the real frame, then the output read back to find which rows survive:

| Measurement | Value |
|---|---|
| Screen drawn inside the frame at | 0.7455 scale |
| Rounded corners eat the top | **153 px of source** (51 pt), symmetrically |
| Dynamic Island obscures | **nothing** |
| **Inset the content by** | **62 pt** (186 px at 3×) |

The island is drawn, and it is drawn **in the bezel above the screen** rather than over the
screenshot: at every column from 25% to 75% across, source row 0 survives, and the obscured columns
are 136 of 984, all of them at the two ends in a symmetric curve. So the obstruction is the corner
radius alone, and it is *smaller* relative to the panel than Android's punch-hole was.

62 pt rather than the 51 pt that would just clear it, because the band has a second job: it has to
read as a status bar, and 62 pt is the real top safe-area inset on the 6.9" phone this preset draws.
The gate is the one Android used — **the top 186 px of every frame is a single colour**, asserted
over all five.

### 2.5 Rendering

| Preset | Dimensions | Used for |
|---|---|---|
| `ios-phone` | 1320 × 2868 | the whole set — App Store, iPhone 6.9" |
| `ipad-13` | 2064 × 2752 | **not used** — phone-only, see §6.2. Listed so a later iPad pass knows the preset exists |

`ios/store/render-store-art.sh` mirrors `android/play/render-store-art.sh`: the same
`npx --yes -p storeshots-mcp storeshots` CLI, the same `compose` then `validate` per panel, the same
`showcase` strip for review. Three of Android's findings are taken as settled rather than re-learned:

- **One layout variant for the whole set.** Every panel is `text-top`, so the device sits at the same
  height throughout. Variety comes from the headlines and the screens.
- **No headline states a count**, and the nouns come from `docs-v3` — *verification result*, and its
  *status* and *message*, which are also the words on the app's own status pills.
- **The output directory holds store art and nothing else.** Android's review strip sitting among the
  panels failed its release lane, which validated it as a phone screenshot. Here the strip is written
  to `ios/store/showcase.png`, a level above `ios/store/screenshots/`.

There is one iOS-specific trap the tool already absorbs, recorded so nobody debugs it twice:
**storeshots flattens the alpha channel on every `compose` output**, because App Store Connect
rejects a screenshot that carries one. `showcase` does **not** — the strip comes back as RGBA. That
is a sharper version of Android's "the directory must hold only store art": here the strip would fail
validation on a property invisible to the eye, so it is written a level above the panels and the
listing test asserts the directory holds exactly five files.

### 2.6 PII discipline

Unchanged from Android §2.4, and re-proved against this tree in §6.4: the sandbox test identities
cover every state the art needs, `sample_token_simulate` mints a fixture token so the session card
and countdown are shown without a real JWT existing, and `seedJobs` populates the list. The whole set
is capturable with zero real credentials.

## 3. Signing and upload — bare xcodebuild, and no team in the tree

The Android plan's §3 is about reusing a key. There is no key to reuse here, so this section is about
the thing that replaces it: **nothing about the signing identity is committed, and the pipeline is
still reproducible.**

**Three secrets, mirroring the three Play ones**, all repository secrets and never tree contents:

| Secret | What it is | Play counterpart |
|---|---|---|
| `APP_STORE_CONNECT_ISSUER_ID` | the App Store Connect API key's issuer UUID | — |
| `APP_STORE_CONNECT_KEY_ID` | the key's 10-character id | — |
| `APP_STORE_CONNECT_PRIVATE_KEY` | the `.p8` private key, verbatim | `PLAY_STORE_SERVICE_ACCOUNT_JSON` |
| `APPLE_DEVELOPMENT_TEAM` | the 10-character team id | — |

The team id is a secret here **not because it is confidential** — it ships inside every distributed
binary's provisioning profile — but because the repository is going public and `AGENTS.md`'s
never-commit list names team identifiers. Treating it as a secret costs nothing and removes the
question.

**Why an API key rather than an app-specific password.** The key authenticates `xcodebuild` for both
upload and — crucially — for `-allowProvisioningUpdates`, which is what lets the runner fetch a
distribution certificate and profile instead of having them baked into a keychain the repository
would have to carry. That is the whole reason a fastlane match-style credential store is not needed:
Xcode's own cloud signing does the job, given a key.

**The export-options plist is committed** (`ios/store/ExportOptions.plist`) and carries no team:
`teamID` is substituted at export time from the secret. It declares `app-store-connect` as the
method, `automatic` signing, and `uploadSymbols` true so crashes symbolicate.

**`ios/verify.sh archive` is the only caller.** As with the other phases, the steps live in the
script and the workflows name a phase — so a bundle built by hand and a bundle built by CI go through
the same code, and the local contract cannot drift from the gate.

### 3.1 The build number, derived the way Android derives versionCode

`git rev-list --count HEAD`, computed in the workflow and passed as `CURRENT_PROJECT_VERSION` on the
`xcodebuild` line. One monotonic source across both lanes, which is Android's §3.1 defect not being
ported: v11 computed it two different ways on two tracks and made the pair unuploadable.

`MARKETING_VERSION` stays the hand-bumped `1.0`, as `versionName` did — it is what the settings
footer renders and it should change when a person decides it has.

**Two build-time refusals, so a misconfigured lane fails before it burns a number** — the same
argument that put `-PREQUIRE_UPLOAD_SIGNING` in Android's Gradle file rather than in a workflow step:

- an archive with no `DEVELOPMENT_TEAM` fails at the archive step, not at export
- an archive whose `CURRENT_PROJECT_VERSION` is unset or non-numeric fails before it is built, because
  the `?: 1` equivalent — Xcode silently keeping the committed `1` — is reachable from a publish lane

### 3.2 What the two publish workflows do differently

`publish-testflight.yml` and `publish-app-store.yml`, both `workflow_dispatch` only, both
`concurrency` without `cancel-in-progress`, both `permissions: contents: read`.

- **Dispatch only, permanently for the App Store lane and for now for TestFlight.** Android's
  internal lane is still dispatch-only for the same reason: the first upload fixes the signing
  identity and creates the listing, and that is an owner action. Adding `push: branches: [main]` to
  TestFlight later is a one-line change — and it needs a **path filter**, or a docs-only merge ships
  a build. That is Android's §7.4 finding, inherited before it is earned.
- **Both lanes compute the build number with the same command**, per §3.1.
- **Secrets reach `xcodebuild` as environment variables, never as command-line arguments**, so the
  team id and key never appear in the runner's process list. The `.p8` is written to
  `~/.appstoreconnect/private_keys/` and deleted in an `always()` step.
- **Neither lane can be reached from a fork PR**, because neither has a `pull_request` trigger.

## 4. The icon — already done, and deliberately untouched

`svgs/ios.svg` renders to `ios/App/Assets.xcassets/AppIcon.appiconset/AppIcon1024.png` through
`scripts/generate_app_icon.py`, which drops the corner radius (iOS masks the icon itself), drops the
alpha channel (App Store Connect rejects one), and insets the artwork to 0.90 because the home-screen
superellipse clipped the badge at full size. `scripts/app-icon.lock` records the source hash and the
scale, and `ios/verify.sh` fails if the asset is stale.

That is the whole of Android's §4 already paid for, in the shape iOS needs. Nothing in this plan
changes it. Recorded here only so the next reader does not go looking for the missing half.

## 5. The copy — the product paragraphs travel, the fields do not

`play-release-android.md` §8 ruled that all four listings share one set of product paragraphs, and
`android/play/full-description.txt` is that set. The App Store description takes it unchanged, which
means a `docs-v3` change still has one blast radius rather than four.

**What the App Store forces to differ is field shape, not voice.** Its limits are not Play's, and one
of them does not fit:

| Field | App Store limit | Play counterpart | Action |
|---|---|---|---|
| Name | 30 | title, 30 | "UseSmileID Sample" (17) — unchanged |
| **Subtitle** | **30** | short description, 80 | **new copy needed**: Play's is 67 characters |
| Description | 4000 | full description, 4000 | unchanged (3030) |
| Promotional text | 170 | — | new, and editable without a build |
| Keywords | 100 | — | new |
| What's New | 4000 | release notes, 500 | takes Play's, which already fits |

The subtitle is therefore the only line written fresh, and it is written to the same rule: name the
thing, state no count, no superlative, no second person. **"Reference app for Smile ID"** — 26
characters, and it says what the app is rather than what it is for.

**Promotional text carries the sandbox note**, because it is the one field editable without a new
build and the note is the thing most likely to need editing.

**Keywords are concepts, not the name.** Apple already indexes the name and subtitle, so repeating
"Smile ID" or "sample" there wastes the budget. They also carry no trademark we do not own.

**Release notes are written by a person**, which is Android's §5 ruling. v11 generated them from
`git log` and shipped PR numbers and emoji to partners; that stops here and it stopped there.

Limits are asserted rather than counted once, because both stores truncate silently instead of
rejecting. Android's `UseSmileIDSamplePlayListingTest` is a JVM unit test; iOS takes
`scripts/check_store_listing.py` instead, and the divergence is deliberate. The checks read files and
touch no app code, so as an XCTest they would have cost a full simulator build in every lane that
wanted them — and `ios/verify.sh archive` could not have run them at all without pulling a simulator
into a phase that otherwise needs none. A python `--check` is also the shape this repo already uses
for committed artefacts (`sync_design_tokens.py`, `generate_ios_icons.py`, `generate_app_icon.py`),
so the gate runs in both `checks` and `archive`, and a hand-built archive is held to the same rule as
a CI one.

## 6. The answers that come from the code

### 6.1 App Privacy — Play's answers hold, and the mapping is the work

Android's §6.1 established the behaviour: the app collects name, other personal info, photos and
device IDs; it shares device IDs, crash logs and diagnostics, and that sharing is Sentry. **The
behaviour is identical on iOS** — same SDK, same Sentry, same submission path — so the answers carry
over and only their names change.

| Play data type | App Store equivalent | Collected | Linked | Tracking |
|---|---|---|---|---|
| Personal info — Name | Contact Info → Name | Yes | Yes | No |
| Personal info — Other info | Identifiers → User ID; Sensitive Info | Yes | Yes | No |
| Photos and videos — Photos | User Content → Photos or Videos | Yes | Yes | No |
| Device or other IDs | Identifiers → Device ID | Yes | No | No |
| App activity — Other actions | Usage Data → Product Interaction | Yes | No | No |
| App info and performance — Crash logs | Diagnostics → Crash Data | Yes | No | No |
| App info and performance — Diagnostics | Diagnostics → Performance Data | Yes | No | No |
| — (declared by the SDK's manifest, not by Play) | Location → Precise Location | Yes | Yes | No |

**Tracking is "No" on every row, and that is a claim with teeth.** Apple defines tracking as linking
this app's data to third-party data for advertising or data-broker purposes. Nothing in the graph
does that: Sentry's own manifest declares `NSPrivacyTracking` implicitly absent and Lottie's declares
it `false`. If an advertising or attribution SDK is ever added, this answer changes and App Tracking
Transparency becomes a requirement.

The whole table lives in `docs/app-store-privacy.md`, which is the iOS counterpart to
`docs/play-data-safety.md` — filled in from the page rather than from memory, and updated in the same
change as any behaviour that moves an answer.

### 6.2 iPad — the UI stretches, it does not adapt. Ship phone-only

Android's §6.2 read the code before deciding; the same read on this tree gives the same answer, from
evidence that is if anything blunter:

- **No size classes anywhere.** `horizontalSizeClass`, `verticalSizeClass`, `UserInterfaceSizeClass`,
  `NavigationSplitView` and `userInterfaceIdiom` return **zero hits** across `ios/App/Sources` and
  `ios/SampleUI/Sources`. There is no breakpoint in the app to hit.
- **Exactly one width is verified.** `UseSmileIDSampleGoldenTest.swift:109` pins every one of the 207
  baselines to `width = 393`. There is no evidence about any other width, on iOS as on Android.

So an iPad build lays out and runs, and what it produces is a single-column phone layout inflated to
thirteen inches. **`TARGETED_DEVICE_FAMILY` is set to `1`**, which is the ruling, and it does three
things beyond honesty: it removes the obligation to supply 2064 × 2752 screenshots, it removes an
iPad review pass against a layout with no iPad in it, and it makes the "1,2" that is there today a
decision rather than an XcodeGen default.

**Reversible on purpose**, exactly as Android recorded it. Adding iPad later is a feature — size
classes, a two-pane verifications list, a second golden width — not a release chore. A device family
can be widened in a later version; it is the narrowing that would be a problem, and this narrows
before the first upload rather than after.

### 6.3 The privacy manifest — what the graph declares, and what it does not

Checked rather than assumed, because a manifest that is complete for the app and silent about its
dependencies is the common way this ships broken.

| Package | Version | Ships `PrivacyInfo.xcprivacy` | Declares |
|---|---|---|---|
| `lottie-spm` | 4.6.1 | **yes** | FileTimestamp (C617.1) |
| `sentry-cocoa` | 9.26.1 | **yes** | UserDefaults (CA92.1), SystemBootTime (35F9.1), FileTimestamp (C617.1); crash, performance and diagnostic data |
| `ios-spm` `UseSmileID` | 12.1.1 | **yes** | UserDefaults (CA92.1); PreciseLocation, PhotosorVideos and UserID (linked), CrashData and OtherDiagnosticData |
| `ios-spm` `Bridge`, `VisionFace`, `VisionDocument` | 12.1.1 | **yes** | `NSPrivacyTracking: false` only — they collect nothing themselves |
| `kamera-spm` | 1.0.6 | **no** | — but it links only CoreGraphics, CoreMedia, CoreVideo and ImageIO, and its binary references no required-reason API, so it has nothing to declare |

**A correction, recorded because the first draft of this section got it wrong.** It said `ios-spm`
ships no manifest. It does — one in every slice of all four XCFrameworks, byte-identical to the
source repository's. The search that produced the wrong answer ran over `SourcePackages/checkouts/`,
which holds the SPM wrapper package; the binaries land in `SourcePackages/artifacts/`, and that is
where the manifests are. A finding about a binary dependency has to be made against the binary.

Two consequences, and only one of them is this repository's to fix.

**The app declares its own, and only its own.** Apple merges a dependency's manifest into the privacy
report at build time, so re-declaring Sentry's `UserDefaults` access here would be noise. The app's
own required-reason usage is exactly `UserDefaults`, at two call sites, both of which are the app
reading its own container — reason **CA92.1**. Nothing else in `ios/App/Sources` or
`ios/SampleUI/Sources` touches a required-reason API: file timestamps, disk space, system boot time
and active keyboards return no hits.

**The SDK's manifest declares Precise Location, and that has to reach the App Privacy form.** The SDK
reads `CLLocationManager.location` — the cached fix — whenever the host already holds the permission,
and never asks for it (`UseSmileIDMetadataFactory.resolveGeolocation`). This app never asks either, so
on this app the fix is always `nil` and nothing is sent. But the privacy report Xcode generates from
the archive merges the SDK's manifest, and a reviewer comparing that report with the form sees
Precise Location in one and not the other. §6.1's table therefore carries a Precise Location row,
marked as coming from the SDK's declaration rather than from anything this app does.

### 6.4 Fixture defaults — re-audited before the store build

Android shipped three fictional partners because REL-A10 audited what the flows *seed* and what the
frames *show*, and a state holder's constructor default was neither (`play-release-android.md` §7.4).
§8 turns that into a standing instruction for the other three ports, so it is executed here rather
than assumed from the iOS port having fixed its own version of it in #57.

Every default read, on this tree:

| Holder | Default | Fixtures reachable by |
|---|---|---|
| `UseSmileIDSampleProfiles` | `starter()` — one profile, `"Default profile"`, no person | `seedProfiles` |
| `UseSmileIDSampleJobStore` | empty; `seedFixtures` has one caller | `seedJobs` |
| `UseSmileIDSampleUserDetails` | every field `""` | a profile's saved defaults |
| `UseSmileIDSampleIdDetails` | `country` and `idType` nil, `idNumber` `""` | user input |
| `UseSmileIDSampleSettings` | six booleans, the design's shipped defaults | — |
| `UseSmileIDSampleTokenSession` | none; a session exists only once scanned or simulated | `sample_token_simulate` |
| `Loupe` | `isRecording = false` | the settings row |

The only non-empty string default in `State/` or `Data/` is `"Default profile"` itself, which is the
absence of a fixture rather than one. **Clean, and the reason it is clean is a test** —
`UseSmileIDSampleProfilesTest` holds both the plain default and the launch choice, which is the form
Android's fix took too.

### 6.5 App Review access — no special access, and the build agrees

Android's §6.3 ruled this and made the ruling's truth a test rather than a checklist line, because
**Simulate is not debug-gated**: a reviewer mints a fixture token from the scan sheet and reaches the
token session, its bindings, its countdown, the expiry state and the flow handoff, with no credential
we would have to issue.

The same is true here and for the same reason, and the iOS suite already proves the part that could
rot: `UseSmileIDSampleLaunchArgumentUITests` runs the probes gate **under Release configuration**
(`ios/verify.sh`, the release probes step), which is the configuration-blind assertion Android's test
was added to make. What that leaves is the scan sheet's Simulate affordance surviving release, which
`ios/verify.sh`'s release probes step asserts by running
`testSimulateLinksASessionAndTheProductsStripCountsItDown` under Release configuration — the
declaration's truth depends on it, so it is asserted rather than remembered.

App Review notes therefore say: no account required, no special access, and Simulate is the
affordance that reaches the session states.

### 6.6 The four privacy-sensitive references, and what each one owes

Read out of the shipped binaries with `nm -u`, then traced to the SDK source, then calibrated against
what the three existing Smile ID samples ship — because a usage string is cheap and a wrong one is a
rejection either way.

| Reference | Where, and what for | Owes | Ruling |
|---|---|---|---|
| `CLLocationManager` | `UseSmileIDMetadataFactory` reads the cached fix when already authorised; never requests | `NSLocationWhenInUseUsageDescription` | **Required.** The upload check is on the reference. All three Smile ID samples ship it |
| `PHPickerViewController` | `UseSmileIDDocumentCaptureControls`, gallery import of a document | `NSPhotoLibraryUsageDescription` | **Shipped, for parity.** PHPicker is out-of-process and needs no permission — the SDK's own comment says so — but every Smile ID sample ships the string and the SDK's manifest declares the type |
| `LAContext` | `UseSmileIDPrivileges`: `canEvaluatePolicy` and `biometryType` for device-state metadata; never `evaluatePolicy`, so it never prompts | `NSFaceIDUsageDescription` | **Not shipped.** No Smile ID sample carries it and v11 is live with the same reference, which is the evidence the check does not fire on it |
| `CMMotionManager` | `DeviceOrientationTracker`, accelerometer for capture orientation | nothing — iOS has no purpose string for the motion manager | **Nothing owed** |

**One functional gap the same comparison found, and it is not release work.** The SDK's documentation
(`Document-Capture-Orientation.md`, and `docs-v3` *performing-a-verification*) says document capture
on iOS needs the host to return `UseSmileIDOrientationController.shared.mask` from
`application(_:supportedInterfaceOrientationsFor:)` — *"the hook is what matters; it outranks
Info.plist"*. The v12 SDK's own sample wires it in its `AppDelegate`. This app does not: it has no
`AppDelegate`, and no `UISupportedInterfaceOrientations` either (iOS's default gives it portrait and
both landscapes, which satisfies the plist half). Without the hook the SDK can request a rotation but
not hold it. This is app behaviour, not listing work, and it belongs in a small PR of its own before
the App Store submission rather than before TestFlight — recorded in §7.2.

**§6's answers.** 6.1 is transcribed into `docs/app-store-privacy.md` with Play's mapping as the

it a deferral has not changed. 6.3's manifest table was read out of the resolved checkouts rather than

asserted under Release configuration rather than remembered.

**The defect the gate found, which reading could not have.** `CURRENT_PROJECT_VERSION` on the
`xcodebuild` line reached the build settings and **not the bundle**: XcodeGen had baked `1` into the
generated Info.plist as a literal, so the archive carried `CFBundleVersion = 1` while every refusal in
§3.1 passed. Every upload after the first would have been rejected, and the refusals designed to stop
exactly that would have said nothing. `CFBundleVersion` and `CFBundleShortVersionString` are now the
build-setting placeholders, the archive reads 76 for commit 76, and the release lane asserts it against
the run number rather than trusting it.

**One tooling trap worth writing down**, because it cost a confusing five minutes and would cost more
in a lane: `plutil -extract <key> raw <file>` **rewrites the file in place** unless `-o -` is passed. A
diagnostic that reads a plist silently replaced the archived app's Info.plist with the extracted value,
and every later check on it then failed for a reason that had nothing to do with the build. The
release lane's assertions all pass `-o -`, with a comment saying why.

### 7.2 What is owed, and what it does not block

- **The camera panel** needs a device, exactly as Android's REL-A9 does. The composer already has its
  slot and its headline; five panels are rendered and Apple requires one, so it blocks nothing.
- **The `verification_details` panel is the weak one**, and it is weak for precisely the reason Android
  recorded: hiding the debug result card leaves the screen sparse. That hiding is not optional — a
  plain release install has `showProbes` false, and store art showing a state a reviewer's own build
  cannot reach would be a misdeclaration, not a cosmetic choice. Ship it, drop to four, or swap in a
  denser state; screenshots are editable on a live listing at any time.
- **The products panel's lower third is empty** at 440 pt, where the goldens' 393 pt fills it — wider
  cards make a shorter grid. It does not show in the composed panel, because the frame crops the device
  below that point. Recorded so nobody re-finds it in the frame and assumes the panel is broken.
- **The two stores show different demo data for the same app.** iOS renders `Kobo Bank` / `KB`;
  Android renders `UpTech Finance` / `KA` (`android/sample-ui/src/test/kotlin/.../StoreArtTest.kt`).
  Both are fixtures, so neither leaks anything — but a partner comparing the listings sees two
  organisations for one app, which `AGENTS.md`'s uniform-visuals rule exists to prevent. Aligning iOS
  is a one-line change; aligning Android means re-rendering its committed art. **Owner's call, and it
  should end in `spec/` so the two cannot drift again.**

- **The orientation hook is not wired** (§6.6). `UseSmileIDOrientationController.shared.mask` from
  `supportedInterfaceOrientationsFor` is what the SDK documents and what its own sample does; this app
  has no `AppDelegate` to return it from. A `@UIApplicationDelegateAdaptor` of a few lines. Before the
  App Store submission, not before TestFlight — a tester on TestFlight is who finds out whether
  document capture holds landscape.

### 7.3 What the review caught that the build did not

Three passes over the branch found defects no green lane would have: worth recording because each is
a shape that will recur in the Flutter and Expo ports.

- **`archive` ran as part of `all`.** `runs()` is true for every phase under `all`, so the bare
  `ios/verify.sh` — the definition of done — demanded a signing identity a fresh clone has not got and
  could never exit 0. The phase's own header comment claimed the opposite. Gated on `$PHASE` directly now.
- **The phone-only gate proved nothing.** `plutil -extract UIDeviceFamily.0` reads `1` for `[1,2]` as
  well as for `[1]`, so the assertion added to catch the iPad regression would have passed through it.
  The whole array is compared now.
- **The release-check lane could never have passed.** It set `DEVELOPMENT_TEAM` from a secret but
  imported no certificate, so automatic signing had nothing to find — and taking a secret on a
  `pull_request` trigger is what `AGENTS.md` forbids outright. It archives unsigned now
  (`CODE_SIGNING_ALLOWED=NO`), which needs no credential and still proves every declaration.
- **The v11 comparison caught a seventh blocker.** No amount of reading this tree would have found the
  missing `NSLocationWhenInUseUsageDescription`, because nothing in this tree uses location; the SDK's
  binary references `CLLocationManager` and the upload check runs on references. The three existing
  Smile ID samples all ship the string, which is the kind of fact only a sibling can tell you.
- **The same comparison falsified this plan's own SDK-manifest finding.** §6.3 records how.
- **`render-store-art.sh --frames` could ship the previous release's art in silence.** The `|| true`
  that record mode requires also swallowed a compile error; the script then composed from the stale
  frames and rewrote the lock from them, so every downstream gate agreed. It now compares the frames'
  hashes across the run and fails when the recorder wrote nothing.

## 8. Parity — what Flutter and Expo inherit

**Unchanged from Android, and now proved twice:** capture from committed deterministic renders; one
layout variant for the whole set; headlines from `docs-v3` nouns with no count; fixture-only data in
every published frame; store art committed and staleness-gated; the art directory holding nothing
else; release notes written by a person; one monotonic build number across every lane, computed once.

**What the iOS release learned that Flutter and Expo should not re-learn:**

- **The golden width is probably not the store width.** Android's store-art test existed because
  goldens and store art must not share a directory; iOS needed one for that reason *and* because its
  goldens render at 393 pt while the store preset is 440 pt. Check the arithmetic before assuming a
  golden can be a frame — the mismatch is invisible until a text-heavy panel is rescaled.
- **The Dynamic Island costs 68 pt, not Android's 40.** Measure it through the frame; §2.4 is the
  method, and the number will differ again on a different preset.
- **Two of the four blockers fail after a successful upload, not during the build.** The
  export-compliance key and the privacy manifest both let a green lane deliver nothing. They are
  cheap to add and expensive to discover, so they go in before the first archive rather than after
  the first rejection.
- **`TARGETED_DEVICE_FAMILY` defaults to "1,2"** in an XcodeGen project that does not mention it,
  which is a decision nobody made showing up as an iPad review obligation.
- **`nm -u` the SDK binaries before the first upload.** Four privacy-sensitive classes are referenced
  and one of them (`CLLocationManager`) fails the upload without its usage string, though the SDK
  never prompts. Flutter and Expo embed the same XCFrameworks, so both owe the same two strings — and
  the check is on `SourcePackages/artifacts/`, not `checkouts/`, which is also where the SDK's
  manifests turn out to be.
- **A generated Info.plist can silently ignore the build setting you are overriding.** XcodeGen bakes
  `CURRENT_PROJECT_VERSION` in as a literal unless the plist asks for `$(CURRENT_PROJECT_VERSION)`.
  Every version-derivation refusal can pass while the bundle still carries build 1. Assert the number
  in the *built* artefact, never in the settings — the release lane does.
- **`plutil -extract` rewrites the file it reads** without `-o -`. Any lane that inspects a plist and
  then inspects it again is one flag away from checking a file it destroyed itself.
- **Only `compose` flattens alpha; `showcase` does not.** The review strip is RGBA and would fail
  store validation, which is a second, sharper reason the panel directory must hold only panels.

**Platform-specific to iOS:** the `ios-phone` (1320 × 2868) and `ipad-13` (2064 × 2752) presets,
snapshot tests as the off-device renderer with XCUITest for the camera panel, an App Store Connect API
key in place of a service account and an upload key, cloud signing in place of a committed keystore,
and a subtitle field that Play's short description does not fit.
